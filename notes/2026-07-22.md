# KV Cache 为什么还在反复全量搬运？vLLM-Omni 多阶段传输 RFC 解读

- **关注对象：** [RFC #5244](https://github.com/vllm-project/vllm-omni/issues/5244)
- **当前状态：** Open RFC
- **关注时间：** 2026-07-20 至 2026-07-22
- **适用场景：** AR/Prefill 与 DiT/Generation 解耦部署

---

## 写在前面

在大语言模型里，Prefill/Decode 解耦已经形成了一套相对成熟的思路：接收端先查询本地
prefix cache，只为缺失部分分配 block，再让发送端把缺失的 KV 写到目标地址。传输完成
以后，请求才重新进入可调度状态。

到了多模态生成模型，链路变长了。以 Hunyuan、BAGEL 一类 AR-DiT 架构为例，AR 阶段
先理解文本和参考图像，DiT 阶段再在多个 diffusion step 中复用这部分上下文。今天的
vLLM-Omni 已经能把 AR KV 传给 DiT，也能在去噪过程中复用 prompt KV；问题是 DiT
还没有真正“拥有”这块 cache。

结果是系统虽然能跑，但数据移动和调度方式还比较粗：同一请求可能反复传输完整 cache，
排在队首的请求等待传输时会挡住后面的可运行请求，cache 的分配、驻留和释放也缺少统一
管理。

[RFC #5244](https://github.com/vllm-project/vllm-omni/issues/5244) 想解决的，正是这组
问题。它不只是增加一个传输接口，而是试图回答四个更基础的问题：

1. DiT 端应该由谁管理 KV cache？
2. 请求还在等 KV 时，调度器能不能继续运行别的请求？
3. AR 到 DiT 的传输怎样做到只搬缺失页面？
4. 哪些能力应该复用 vLLM，哪些语义必须留在 vLLM-Omni？

---

## 一、当前瓶颈不只是“传输慢”

RFC 描述的当前 AR → DiT 路径大致如下：

```text
AR 侧 paged KV
    ↓ gather / flatten
临时 tensor 或 bytes
    ↓ connector
DiT 目标 tensor
    ↓ concat / clone
模型私有 KV 对象
```

这条路径有三个直接成本。

### 1.1 已经存在的 KV 仍可能被重复传输

DiT 端没有完整的本地 prefix 查询、目标 block 预分配和 missing-only transfer 流程，
因此很难像 vLLM 的 P/D 解耦那样，只请求本地尚未命中的 suffix。请求即使已经传过一部分
稳定上下文，后续仍可能再次搬运完整 cache。

### 1.2 传输等待藏在 runner 内部

当前 DiT 调度接近 FIFO。请求进入 runner 后再等待远端传输或 H2D copy，GPU 执行路径
也跟着停下来。真正的问题不是某一次 copy 多花了几毫秒，而是“等待数据”和“可以计算”
没有在调度层被区分。

### 1.3 DiT cache 仍是模型私有的连续 tensor

AR 和 Generation 阶段已经使用 vLLM 风格的 paged KV 管理，DiT 则主要依赖各模型自己
维护的 tensor。没有统一的 page、引用计数和驻留状态，就很难同时处理 HBM 命中、CPU
offload、远端缺失、取消和超时。

---

## 二、RFC 的核心：让 DiT 真正拥有 cache

RFC 给出的目标架构可以浓缩成三个组件：

- **`DiTKVCacheManager`**：管理语义页面与物理 block，记录 HBM、CPU 和远端驻留状态，
  负责分配、引用计数、保留与释放。
- **cache-aware scheduler**：在请求进入 denoising batch 前先做 cache plan，不再让 runner
  隐式等待。
- **显式 transfer session**：把发送方租约、接收方预留、传输完成、取消、超时和失败放进
  同一个生命周期。

整体关系如下：

```text
Orchestrator
    │ 建立 session，传递路由和 connector 信息
    ├───────────────────────────────┐
    ▼                               ▼
AR / Prefill                    DiT / Generation
vLLM KVCacheManager             DiTKVCacheManager
source-page lease               lookup / reserve / refcount
    │                               │
    └──── receiver-driven plan ─────┘
                    │
                    ▼
          sender-push / RDMA WRITE
                    │
                    ▼
          DiT BlockTable + paged attention
```

这里最重要的变化，是 cache 的所有权从“模型拿到一个 tensor 再自行处理”，转移到了
manager、scheduler 和 runner 共同维护的 page lifecycle。

---

## 三、调度器要区分“没数据”和“没容量”

当 DiT scheduler 收到一个请求时，它不应该立刻把请求塞进 denoising batch，而是先回答
三个问题：需要哪些稳定页面、这些页面在哪里、当前还有多少传输和 HBM 预算。

RFC 设计了四类结果：

```text
HBM 全命中  → acquire refs                         → READY
CPU 命中     → reserve HBM + async H2D             → WAITING_FOR_LOCAL_KVS
远端缺失     → reserve destination + receive pages → WAITING_FOR_REMOTE_KVS
容量不足     → 等待、驱逐或抢占                     → WAITING
```

这样做的收益并不是让单次 RDMA 本身变快，而是让调度器看见“哪些请求已经可以计算”。只要
还有 `READY` 请求，DiT 就可以继续组 batch，不必被队首的远端 miss 拖住。

换句话说，这份 RFC 真正想消除的是 **GPU bubble**，missing-only transfer 只是其中一环。

---

## 四、为什么推荐 receiver-driven + sender-push

这两个词放在一起容易让人困惑：既然是 sender-push，为什么又叫 receiver-driven？

因为目标地址必须先由接收端决定。推荐流程是：

1. DiT 查询本地 cache，只为缺失页面预留目标 block。
2. DiT 把缺失页面和目标地址发给 AR。
3. AR 保持 source-page lease，并通过 Mooncake RDMA WRITE 主动写入目标地址。
4. DiT 收齐所有 rank 的数据后 commit reservation，再把请求标记为 `READY`。
5. 终态 ACK 返回 AR，AR 才能释放源页面。

这种方式同时满足两件事：接收端掌握 cache 命中与目标分配，发送端又能尽早发起传输并与
计算重叠。后续代码讨论也指出，Mooncake Transfer Engine 已经接近这种行为；需要明确的
是首期以哪条 transport path 为准，以及 Store path 如何处理 completion 和 cleanup。

---

## 五、哪些复用 vLLM，哪些留在 Omni

这是 RFC 中影响面最大的设计取舍。

适合从 vLLM 复用的，是通用的 paged-cache 机制：`BlockPool`、`BlockTable`、slot mapping、
offload/copy 支持，以及 connector 的完成通知、source lease 和 delayed-free 能力。

必须留在 vLLM-Omni 的，是生成模型语义：

- stable context 与 dynamic latent 的边界；
- CFG 分支和 diffusion-step admission；
- 多阶段 DAG、artifact readiness 与 streaming；
- 一次请求中多个独立 transfer session 的聚合。

RFC 发布后的讨论进一步收敛出一个 hybrid 方向：上层继续暴露
`OmniConnectorBase`，让 scheduler 和 runner 使用 Omni 的 session 与 artifact 语义；下层
具体 connector 则继承 vLLM 的 `KVConnectorBase` / `ECConnectorBase`，避免重新实现 paged
KV 传输和完成协议。

这个分层比简单的“完全自研”或“完全复用”更符合 Omni 的现实：通用机制向上游靠拢，
多阶段语义由 Omni 自己负责。

---

## 六、还有一个必须回答的问题：为什么不直接复用完整 KVCacheManager

讨论中出现了一个很关键的现状：`experimental/ar_diffusion` 已经在 DiT engine 中复用了
完整的 vLLM `KVCacheManager` 和 paged KV stack。它未来计划迁移到这份 RFC 的架构，
因此它不是竞争方案，而是一个已经存在的验证样例。

但这里也有张力：实验实现复用完整 `KVCacheManager`，RFC 当前更倾向于新建只复用
`BlockPool` 的 `DiTKVCacheManager`。如果最终选择后者，就需要明确说明完整 manager 在
DiT 语义下究竟哪里不适用；否则迁移反而会降低复用层级。

这可能是实现开始前最值得尽早定下来的问题，因为它会影响 scheduler API、connector
metadata 和后续每个模型的迁移成本。

---

## 七、这份 RFC 还不能证明性能收益

RFC 预期 missing-only transfer、异步 copy 和 cache-aware scheduling 能减少传输量与
GPU 空闲时间。这个方向合理，但目前还没有 A/B 数据，因此不能把“预期收益”写成“已经
提速”。

后续至少应该固定一个 pilot model，并记录：

- AR → DiT 实际传输字节数；
- DiT GPU idle ratio 或等待时间；
- cache hit rate 与 HBM/CPU/remote 分布；
- 相同 workload 下的端到端吞吐与延迟；
- 取消、超时和 worker failure 时是否存在页面泄漏或 stale completion。

另外还有三个语义风险值得继续观察：CFG 分支是否真的能共享页面、dynamic latent 如何在
step 之间被结构性地禁止复用，以及不同 DiT pipeline 从连续 tensor 迁移到 paged cache
的成本。

---

## 八、总结：它要优化的是“等待关系”，不只是 KV copy

这份 RFC 最有价值的地方，是把 AR → DiT KV transfer 从 runner 内部的一次同步动作，
提升成 scheduler 可以理解和管理的系统资源。

如果最终设计落地，理想状态会是：DiT 只接收本地缺失的稳定页面；等待远端 KV 的请求不会
挡住已经 ready 的请求；source lease、target reservation 和 completion 由 session 串成
完整生命周期；通用 paged-cache 能力复用 vLLM，多模态与 diffusion 语义留在 Omni。

接下来最值得关注的，不是再增加多少接口，而是三个可验证结果：manager 复用边界能否定
下来、首个模型能否完成端到端迁移、以及传输字节和 GPU bubble 是否真的下降。
